# 1.3. Реализовать сценарий Web-MVP — подробный план

Этот документ детализирует пункт 1.3 из [основного плана](PLAN.MD). Он
превращает подготовленную в этапе 1.2 основу в первый законченный
пользовательский сценарий: человек регистрируется, создаёт проект ремонта,
добавляет комнаты и покупки, затем видит расходы и остаток бюджета.

Перед началом прочитайте [контракт API](API.MD): он уже фиксирует маршруты,
JSON-форматы, JWT, статусы ответов и правила владения. Если при реализации
нужен другой контракт, сначала согласованно измените `API.MD`, а потом код,
тесты и frontend.

## Результат этапа

Web-приложение позволяет пользователю:

1. зарегистрироваться и войти;
2. создать и выбрать свой проект;
3. настроить тип объекта, адрес и плановый бюджет;
4. создать комнаты;
5. создать, отредактировать, отфильтровать и удалить покупки;
6. увидеть обзор проекта, расходы по категориям и остаток бюджета.

Каждый ресурс принадлежит текущему пользователю. Данные другого аккаунта не
видны через API и недоступны из интерфейса. Backend, frontend, миграции и
автоматические проверки остаются согласованы.

## Принципы работы

- Реализуем вертикальными срезами: сначала модель, миграция, API и тесты
  одного ресурса, затем экран, который использует этот API.
- Не меняем уже применённые миграции. Любое изменение схемы — новая миграция
  Alembic.
- Деньги передаём только десятичными строками и обрабатываем через
  `Decimal`/`NUMERIC`; не используем `float`.
- Хешируем пароль готовой библиотекой. Исходный пароль, `password_hash`, JWT и
  секрет подписи не попадают в логи, ответы API или Git.
- Защита доступа выполняется в backend. Скрыть кнопку в React недостаточно.
- Каждый новый API-маршрут сначала покрываем backend-тестом; затем подключаем
  к нему frontend.
- После каждого небольшого среза запускаем нужные проверки, а не откладываем
  их до конца этапа.

## 2. Подготовить структуру backend и общие правила API

### 2.1. Разделить слои приложения

Сейчас `main.py` содержит приложение и health-check, а пакеты `api`, `schemas`
и `services` пусты. В этом разделе не реализуем регистрацию или проекты: только
готовим повторяемый каркас, в который следующие разделы будут добавлять код.

- [x] Оставить существующие пакеты `core`, `db` и `models` на своих местах и
  создать недостающие модули. После шага структура должна выглядеть так:

  ```text
  backend/app/
  ├── api/
  │   ├── dependencies.py  # зависимости FastAPI: сессия БД, текущий аккаунт
  │   ├── problems.py      # ProblemDetail и фабрика problem+json-ответов
  │   ├── router.py        # корневой API router с prefix="/api/v1"
  │   └── health.py        # технический GET /health
  ├── core/
  │   ├── config.py        # Settings из переменных окружения
  │   └── security.py      # хеширование паролей и JWT (создаётся в 2.2)
  ├── db/
  │   ├── base.py          # SQLAlchemy Base
  │   ├── session.py       # Engine и фабрика Session
  │   └── testing.py       # помощники только для тестовой БД
  ├── models/              # SQLAlchemy-модели таблиц
  ├── schemas/             # Pydantic-модели входящих и исходящих JSON
  ├── services/            # операции предметной области и расчёты
  └── main.py              # создание FastAPI, middleware, handlers, include_router
  ```

  Пустые `__init__.py` оставьте, чтобы Python распознавал пакеты. Не создавайте
  пока router'ы `auth`, `projects`, `rooms` и `purchases`: они появятся вместе
  с соответствующими сценариями.

- [x] Перенести endpoint health-check из `main.py` в `api/health.py`.
  В `api/router.py` создать `api_router = APIRouter(prefix="/api/v1")` и
  подключить к нему router health-check без дополнительного префикса. В
  `main.py` импортировать `api_router` и выполнить один
  `app.include_router(api_router)`. Итоговый URL обязан остаться
  `GET /api/v1/health`, чтобы не сломать существующий тест и Docker health-check.

- [x] Создать `api/dependencies.py` и dependency `get_db_session`.
  Она должна для каждого HTTP-запроса создать `Session` через существующую
  `get_session()` из `db/session.py`, передать её endpoint'у через `yield` и
  закрыть в блоке `finally`. При исключении можно выполнить `rollback()`, но
  не выполняйте `commit()` в dependency: сервис, который успешно изменил
  данные, сам вызывает `db.commit()` и при необходимости `db.refresh()`.
  Endpoint получает сессию в таком виде:

  ```python
  def endpoint(db: Session = Depends(get_db_session)) -> ...:
      ...
  ```

- [x] Разделять код каждого нового ресурса по ответственности. Router читает
  path/query/body, объявляет статус ответа и вызывает сервис; в нём не должно
  быть SQL-запросов или JWT-логики. Сервис получает `Session` и модели,
  выполняет запросы, проверку владения и расчёты. Схема в `schemas` определяет
  разрешённые поля JSON и сериализацию ответа. Например, будущий
  `POST /projects` будет состоять из `api/projects.py` →
  `services/projects.py` → `models/project.py`, а его тело и ответ — из
  `schemas/project.py`.

- [x] Создать в `api/problems.py` единый способ возвращать ошибки контракта:
  заголовок `Content-Type: application/problem+json` и поля `type`, `title`,
  `status`, `detail`, при необходимости — `errors`. Описать небольшие доменные
  исключения или функции для случаев `email_conflict` (`409`) и
  `resource_not_found` (`404`); router'ы и сервисы не должны собирать JSON
  ошибок вручную.

- [x] В `main.py` зарегистрировать обработчики: `RequestValidationError` →
  problem+json со статусом `422`; доменный конфликт email → `409`; доменное
  отсутствие ресурса → `404`. Обработчик JWT из dependency появится в 2.2 и
  будет возвращать `401` с заголовком `WWW-Authenticate: Bearer`. Не заменяйте
  все `HTTPException` глобально: сначала переводите на единый формат только
  ошибки, описанные в `API.MD`.

Проверка: `GET /api/v1/health` по-прежнему возвращает `200` и
`{"status":"ok"}`. Неверный query- или path-параметр у endpoint'а с Pydantic
валидацией возвращает `422`, `application/problem+json` и массив `errors`.
После каждого шага запустите `uv run ruff check .`,
`uv run ruff format --check .` и существующие backend-тесты.

### 2.2. Подготовить настройки безопасности

Этот подраздел добавляет базовые строительные блоки входа. Endpoint'ы
регистрации и входа будут в разделе 5, но после этого шага уже можно безопасно
хешировать пароль, выпускать JWT и извлекать текущего пользователя из токена.

- [ ] Добавить из корня репозитория зависимости: `pwdlib[argon2]` для
  хеширования паролей алгоритмом Argon2 и `PyJWT` для JWT. Зафиксировать их в
  `pyproject.toml` и `uv.lock` командой `uv add "pwdlib[argon2]" PyJWT`.
  Не используйте самописное хеширование, `hashlib` для паролей или собственную
  реализацию подписи JWT.

- [ ] Расширить класс `Settings` в `core/config.py`. Добавьте поля
  `jwt_secret_key`, `jwt_algorithm`, `jwt_issuer`, `jwt_audience` и
  `access_token_expire_seconds`; Pydantic Settings прочитает для них
  одноимённые переменные окружения в верхнем регистре. Задайте безопасные
  постоянные значения для `jwt_algorithm="HS256"`,
  `jwt_issuer="apartment-api"`, `jwt_audience="apartment-web"` и
  `access_token_expire_seconds=900`. `jwt_secret_key` не должен иметь
  значения по умолчанию и должен быть скрыт при печати настроек, например через
  тип `SecretStr`.

- [ ] Дополнить корневой `.env.example` поясняющими строками:

  ```dotenv
  # Сгенерируйте локальный секрет: openssl rand -hex 32
  JWT_SECRET_KEY=replace-with-a-new-random-secret
  JWT_ALGORITHM=HS256
  JWT_ISSUER=apartment-api
  JWT_AUDIENCE=apartment-web
  ACCESS_TOKEN_EXPIRE_SECONDS=900
  ```

  Скопируйте `.env.example` в локальный `.env`, замените только
  `JWT_SECRET_KEY` результатом команды из комментария и убедитесь, что `.env`
  остаётся в `.gitignore`. Значение из примера — заведомо небезопасная
  заглушка, его нельзя использовать для настоящего запуска и нельзя добавлять
  реальный секрет в Git, тестовые фикстуры или логи.

- [ ] Создать `core/security.py` и поместить в него только четыре публичные
  функции. `hash_password(password)` возвращает строку хеша Argon2.
  `verify_password(password, password_hash)` возвращает `True` или `False` и
  не выбрасывает наружу детали неверного пароля. `create_access_token(account_id)`
  принимает UUID аккаунта и возвращает подписанную строку JWT.
  `decode_access_token(token)` проверяет и возвращает claims либо сообщает об
  общем недействительном токене. Пароль и хеш не передавайте в JWT.

- [ ] В `create_access_token` сформировать только claims контракта:
  `sub` — строковое представление UUID аккаунта; `iat` — текущее UTC-время;
  `exp` — UTC-время `iat + 900` секунд; `iss` и `aud` — из Settings; `jti` —
  новый UUID. Подписывать токен секретом из Settings и строго алгоритмом из
  Settings. Не добавляйте email, имя, роль, пароль или `password_hash`.

- [ ] В `decode_access_token` вызвать JWT-библиотеку с явным разрешённым
  списком алгоритмов (`algorithms=[settings.jwt_algorithm]`) и проверкой
  подписи, `exp`, `iss` и `aud`. Дополнительно проверить, что `sub` является
  корректным UUID, а `jti` не пуст. Любую ошибку декодирования, истечения или
  формата преобразовать внутри модуля в одну нейтральную ошибку: наружу нельзя
  сообщать, какая именно проверка не прошла.

- [ ] Добавить в `api/dependencies.py` dependency `get_current_account`.
  Она получает Bearer-токен через `HTTPBearer`, передаёт его в
  `decode_access_token`, загружает `Account` по UUID из `sub` через сессию БД
  и возвращает аккаунт endpoint'у. Для отсутствующего заголовка, неверной
  схемы `Authorization`, плохого/просроченного токена и удалённого аккаунта
  всегда вернуть один problem+json-ответ `401 Unauthorized` с
  `WWW-Authenticate: Bearer`; не раскрывать причину и не возвращать `404`.

Проверка: сгенерированный токен содержит только `sub`, `iat`, `exp`, `iss`,
`aud` и `jti`; корректный токен успешно декодируется, а просроченный токен,
токен с иной аудиторией и изменённой подписью отклоняются. Значение
`JWT_SECRET_KEY` не появляется в выводе, ошибках или Git. Ни одна будущая
response-схема не включает `password_hash`; запрос с неверным Bearer-токеном
возвращает problem+json со статусом `401` и `WWW-Authenticate: Bearer`.

## 5. Реализовать регистрацию, вход и профиль

### 5.1. Схемы и сервис аккаунта

- [ ] Создать отдельные Pydantic-схемы `AccountRegister`, `AccountPublic`,

- [ ] Валидировать имя после trim: от 1 до 100 символов. Email нормализовать

- [ ] Создать сервис регистрации: проверить уникальность email, захешировать

- [ ] Преобразовать нарушение уникальности email в `409 Conflict`. Не
  полагаться только на предварительный `SELECT`: БД остаётся последней защитой

### 5.2. Маршруты и тесты

- [ ] Реализовать `POST /api/v1/auth/register`. Успех — `201 Created` и
  `AccountPublic`; регистрация не выдаёт токен.
- [ ] Реализовать `POST /api/v1/auth/login`. Неверный email и неверный пароль
  должны давать одинаковый `401 Unauthorized` без раскрытия причины. Успех —
  `AccessTokenResponse`.
- [ ] Реализовать защищённый `GET /api/v1/profile`.
- [ ] Реализовать защищённый `PATCH /api/v1/profile` только для `name`.
  Email и пароль не изменяются в этом сценарии.
- [ ] Написать unit-тесты хеширования, проверки срока/issuer/audience JWT и
  преобразования ошибок.
- [ ] Написать интеграционные HTTP-тесты: успешная регистрация, конфликт
  email, успешный/неуспешный вход, профиль без токена, с неверным токеном и с
  корректным токеном, изменение имени.

Проверка: `password_hash` никогда не появляется в JSON или OpenAPI response;
`GET /api/v1/profile` для токена другого пользователя возвращает данные только
этого пользователя.

## 6. Реализовать проекты

- [ ] Создать схемы `ProjectCreate`, `ProjectUpdate`, `ProjectPublic` и
  `ProjectListResponse`. В create нельзя передать `owner_id`, `id`,
  `archived_at` или timestamps.
- [ ] Реализовать сервис `get_owned_project_or_404(project_id, account, db)`.
  Он всегда фильтрует запрос по `project_id` и `owner_id`; это единая точка
  проверки владения.
- [ ] Реализовать `POST /api/v1/projects` и создать проект для текущего
  аккаунта.
- [ ] Реализовать `GET /api/v1/projects` с `limit`, `offset`, `archived`,
  `property_type`, `search` и `sort` по контракту. По умолчанию показывать
  только неархивные проекты.
- [ ] Реализовать `GET /api/v1/projects/{project_id}` и `PATCH`. Разрешить
  изменить название, тип, адрес, бюджет и `is_archived`; `archived_at` ставит
  и очищает сервер.
- [ ] Не добавлять `DELETE /projects/{project_id}` в MVP.
- [ ] Добавить тесты пагинации, поиска, сортировки, архивации/возврата из
  архива, валидации отрицательного бюджета и недоступности проекта другому
  аккаунту.

Проверка: пользователь с двумя проектами видит только свои проекты, а
архивный проект исчезает из списка по умолчанию и появляется при
`?archived=true`.

## 7. Реализовать комнаты

- [ ] Создать схемы `RoomCreate`, `RoomUpdate`, `RoomPublic` и
  `RoomListResponse`.
- [ ] Реализовать `POST /api/v1/projects/{project_id}/rooms` и
  `GET /api/v1/projects/{project_id}/rooms`. Доступ к проекту проверяется до
  создания или выдачи комнат.
- [ ] Реализовать `GET/PATCH/DELETE /api/v1/rooms/{room_id}`. Все операции
  проверяют владельца через проект комнаты.
- [ ] Для `DELETE` с существующими покупками вернуть `409` с problem+json и
  объяснить в `detail`, что сначала нужно перенести или удалить покупки.
- [ ] Добавить тесты чужого проекта/комнаты, сортировки комнат, валидации
  имени и запрета удаления комнаты с покупками.

Проверка: комнату нельзя присоединить к чужому проекту, а удаление пустой
комнаты отвечает `204 No Content`.

## 8. Реализовать покупки

### 8.1. Правила данных

- [ ] Создать схемы `PurchaseCreate`, `PurchaseUpdate`, `PurchasePublic` и
  `PurchaseListResponse`. Все суммы в JSON остаются строками, например
  `"12500.50"`.
- [ ] Валидировать `room_id`: если он указан, комната существует, доступна
  текущему пользователю и относится к тому же `project_id`, что покупка.
- [ ] Валидировать статус:
  - `planned`: `actual_amount` и `purchased_on` равны `null`;
  - `purchased`: `actual_amount` и `purchased_on` обязательны;
  - `cancelled`: `actual_amount` и `purchased_on` равны `null`.
- [ ] При PATCH пересчитывать эти правила из итогового состояния объекта, а
  не только из переданных полей. Например, нельзя изменить статус на
  `purchased` и забыть фактическую сумму.
- [ ] Не интерпретировать пустую строку как деньги, UUID или дату. Клиент
  передаёт `null` для необязательного поля; backend отвечает `422` на
  некорректный тип.

### 8.2. Маршруты и списки

- [ ] Реализовать `POST /api/v1/projects/{project_id}/purchases` и
  `GET /api/v1/projects/{project_id}/purchases`.
- [ ] Реализовать `GET/PATCH/DELETE /api/v1/purchases/{purchase_id}`.
- [ ] Реализовать фильтры `status`, `room_id`, `category`,
  `purchased_from` и `purchased_to`, включая повторяемые `status`,
  `room_id` и `category` по контракту.
- [ ] Реализовать разрешённые сортировки и стабильный порядок с дополнительным
  `id`. Некорректный `sort` или диапазон дат возвращают `422`.
- [ ] После удаления покупки возвращать `204`. Удаление не должно менять
  проект, комнату или другие покупки.
- [ ] Добавить интеграционные тесты создания, изменения статуса, фильтров,
  сортировки, диапазона дат, чужой покупки и проверки принадлежности комнаты.

Проверка: купленная покупка влияет на фактические расходы, отменённая не
участвует в плановой сумме, а данные другого пользователя недоступны.

## 9. Реализовать «Обзор» и «Бюджет»

- [ ] Создать read-only схемы `ProjectOverview` и `ProjectBudget` строго по
  полям из `API.MD`.
- [ ] Реализовать `GET /api/v1/projects/{project_id}/overview`. Он возвращает
  все комнаты с количеством покупок, общее число комнат и покупок, счётчики
  статусов, бюджет, фактические траты, остаток и до пяти последних покупок.
- [ ] Реализовать `GET /api/v1/projects/{project_id}/budget`. Он возвращает
  `planned_budget`, `planned_purchases_total`, `actual_spent`,
  `remaining_budget` и суммы по категориям.
- [ ] Считать `actual_spent` только по `purchased` и `actual_amount`.
  `planned_purchases_total` — сумма плановых значений покупок, кроме
  `cancelled`. `remaining_budget = planned_budget - actual_spent` и может
  быть отрицательным.
- [ ] Считать агрегаты на стороне PostgreSQL (`SUM`, `COUNT`, `GROUP BY`), а
  не загружать все покупки в Python для каждого запроса.
- [ ] Убедиться, что пустой проект отдаёт нули и пустые массивы, а не `null`
  в числовых итогах.
- [ ] Добавить тесты смешанного набора статусов, нескольких категорий,
  отсутствия покупок, превышения бюджета и чужого проекта.

Проверка: ручной расчёт по нескольким покупкам совпадает с ответами
`overview` и `budget` до копейки.

  `/projects/:projectId/overview`, `rooms`, `purchases`, `budget` и

- [ ] Создать единый API-клиент поверх `fetch`: базовый URL из
  `VITE_API_URL`, JSON-заголовки, Bearer token, обработка `204` и
  преобразование problem+json в типизированную ошибку.
- [ ] Описать TypeScript-типы по `API.MD`. Не дублировать «похожие» типы в
  каждом компоненте.
- [ ] Хранить access token для MVP в `sessionStorage`, а текущий профиль — в
  React state. Не писать токен в URL, query-параметры, логи или

- [ ] Создать `RequireAuth`, который не показывает защищённый экран без

- [ ] Создать общий каркас авторизованной части: шапка, название выбранного

Проверка: при обновлении страницы с действующим токеном frontend запрашивает
`GET /profile` и восстанавливает сессию; при `401` возвращает на страницу

- [ ] После входа сохранить токен, запросить профиль и перейти на список

- [ ] Добавить управление отображаемым именем в профиль/меню пользователя

### 11.2. «Мои проекты» и настройки проекта

### 11.4. Покупки и бюджет

- [ ] Реализовать просмотр, изменение и удаление покупки. Перед удалением

## 14. Критерии завершения 1.3

- [ ] Новый пользователь может зарегистрироваться, войти и изменить своё имя.
- [ ] Любой защищённый endpoint требует корректный JWT, а данные другого
  аккаунта отвечают `404`.
- [ ] Пользователь создаёт, изменяет, архивирует и возвращает собственный
  проект; физического удаления проектов нет.
- [ ] Пользователь создаёт, изменяет и удаляет комнаты, а комната с покупками
  не удаляется молча.
- [ ] Пользователь создаёт, меняет, фильтрует и удаляет покупки; статусы и
  суммы валидируются на backend.
- [ ] Overview и budget рассчитывают показатели в соответствии с `API.MD`.
- [ ] Frontend реализует экраны `Мои проекты`, `Обзор`, `Комнаты`,
  `Покупки`, `Бюджет` и `Настройки проекта` в едином визуальном направлении.
- [ ] Локальные и CI-проверки backend/frontend проходят; интеграционные
  тесты не оставляют данных в тестовой БД.
- [ ] Документация описывает реализованное поведение, а не временный
  health-check интерфейс.

## Рекомендуемый порядок коммитов

Держите изменения маленькими и проверяемыми:

1. общая структура API, настройки безопасности и обработчики ошибок;
2. `Project`: модель → миграция → backend API → тесты;
3. `Room`: модель → миграция → backend API → тесты;
4. `Purchase`: модель → миграция → backend API → тесты;
5. auth/profile и проверка владения;
6. overview/budget и тесты расчётов;
7. frontend foundation, auth и список проектов;
8. frontend screens комнат, покупок, обзора, бюджета и настроек;
9. доступность, документация, полный регрессионный прогон.

Не объединяйте в один коммит несвязанные миграции, редизайн и изменение
контракта. Понятная история упрощает review, откат и поиск причины ошибки.
