# 1.2. Собрать основу — подробный план

Этот документ детализирует пункт 1.2 из [основного плана](PLAN.MD). Он рассчитан на обучение: выполняем одну небольшую задачу, проверяем результат и только затем переходим дальше.

## Результат этапа

В репозитории работают API, web-клиент и PostgreSQL. Проект поднимается одной командой Docker Compose, изменения схемы БД проходят через миграции, health-check и тесты выполняются локально и в CI.

## Принципы работы

- Не пишем функциональность проектов и покупок до готовности основы.
- Каждый шаг должен иметь понятный результат и команду проверки.
- Секреты не храним в Git: используем `.env` и `.env.example`.
- Начинаем с минимальной реализации; усложняем, когда появляется практическая потребность.
- Все команды `uv` выполняем из корня репозитория, где находятся `pyproject.toml` и `uv.lock`.

## 3. SQLAlchemy и миграции

В этом разделе появятся три связанных слоя:

```text
модель Account в Python → SQLAlchemy metadata → миграция Alembic → таблица accounts в PostgreSQL
```

SQLAlchemy описывает таблицы классами Python и создаёт подключения к БД. Alembic хранит историю изменений схемы: вместо ручного создания таблиц каждый разработчик применяет одинаковые версии миграций.

### 3.1. Подключение SQLAlchemy

- [x] Создать пакет `backend/app/db` и файл `base.py`.
- [x] В `base.py` создать класс `Base`, наследующийся от `DeclarativeBase`. Все модели будут наследоваться от него.
- [x] Создать модуль подключения, например `backend/app/db/session.py`.
- [x] В нём создать синхронный `Engine` через `create_engine(settings.database_url)`: берём готовый URL из `core/config.py`, не дублируем пароль и хост.
- [x] Создать фабрику сессий `SessionLocal` через `sessionmaker`. Сессия будет единицей работы с БД внутри будущих API-запросов.
- [x] Не создавать соединение при импорте модуля: `create_engine()` только настраивает Engine; настоящее соединение откроется при первом запросе к БД.

На этом этапе используем синхронный SQLAlchemy: у нас драйвер `psycopg`, а первые endpoint'ы пока обычные `def`. Асинхронный вариант намеренно не добавляем, чтобы не смешивать два подхода.

Проверка: маленький временный Python-скрипт или однострочная команда импортирует Engine и выполняет `SELECT 1`. Результат должен быть `1`.

### 3.2. Подготовка Alembic

- [x] Из корня репозитория выполнить `uv run alembic init alembic`. Появятся папка `alembic/`, файл `alembic.ini` и папка `alembic/versions/` для будущих миграций.
- [x] Оставить в `alembic.ini` технические настройки Alembic, но не хранить там адрес БД и пароль.
- [x] В `alembic/env.py` импортировать `settings` из `backend.app.core.config` и передать `settings.database_url` в конфигурацию Alembic программно.
- [x] В `alembic/env.py` импортировать `Base` и присвоить `target_metadata = Base.metadata`. После создания `Account` в разделе 3.3 отдельно импортировать модель в `env.py`, иначе Alembic не узнает о таблице и автогенерация будет пустой.

Проверка: команда `uv run alembic current` запускается без ошибки и использует БД из `.env`.

### 3.3. Первая модель

- [x] Создать пакет `backend/app/models` и файл `account.py`.
- [x] Создать класс `Account(Base)` и задать имя таблицы `accounts` через `__tablename__`.
- [x] Добавить поле `id`: UUID, первичный ключ, значение создаётся автоматически.
- [x] Добавить поле `email`: строка, обязательное значение, уникальный индекс. В базе не должно быть двух аккаунтов с одинаковым email.

На этом шаге не добавляем регистрацию, JWT или проверку пароля — только описание будущей таблицы.

### 3.4. Первая миграция

- [x] Создать миграцию командой `uv run alembic revision --autogenerate -m "create accounts table"`.
- [x] Открыть созданный файл в `alembic/versions/` и прочитать функции `upgrade()` и `downgrade()`. Автогенерацию всегда проверяем до применения: это подсказка Alembic, а не безусловно правильный SQL.
- [x] Применить миграцию командой `uv run alembic upgrade head`.
- [x] Убедиться, что появилась таблица `accounts` и служебная таблица `alembic_version`.
- [x] Проверить историю командой `uv run alembic current` или `uv run alembic history`.

Проверка в PostgreSQL: `docker compose exec <имя-сервиса-БД> psql -U <пользователь> -d <база>`, затем команда `\\dt` покажет список таблиц.

## 4. Контракт API и доступ

Этот раздел пока не добавляет endpoint'ы, модели или JWT-код. Сначала создаём документ `plan/API.MD` — общий договор между backend, web-клиентом и будущими мобильными приложениями. Он позволит реализовывать сценарий 1.3 без неявных решений о маршрутах, формате данных и правах.

### 4.1. Общие правила API

- [x] Создать `plan/API.MD` с заголовком «Контракт API Web-MVP» и кратко указать, что документ фиксирует правила до реализации endpoint'ов.
- [x] Зафиксировать общий префикс для прикладных маршрутов: `/api/v1`. Например, список проектов будет доступен по `GET /api/v1/projects`.
- [x] Указать, что API принимает и возвращает JSON в UTF-8. Для запросов с телом клиент отправляет `Content-Type: application/json`.
- [x] Выбрать стиль именования JSON-полей: `snake_case`, например `created_at` и `password_hash`.
- [x] Зафиксировать формат идентификаторов: UUID передаётся строкой.
- [x] Зафиксировать формат денег: десятичная строка, например `"12500.50"`, а не `float`, чтобы избежать ошибок округления.
- [x] Зафиксировать формат даты и времени: ISO 8601 с часовым поясом, например `2026-08-11T18:30:00+03:00`; дата без времени — `YYYY-MM-DD`.
- [x] Указать успешные статусы: `200 OK` для чтения и обновления, `201 Created` для создания и `204 No Content` для удаления.

### 4.2. Ошибки и пагинация

- [x] Описать единый формат ошибки `application/problem+json` с полями `type`, `title`, `status`, `detail` и необязательным `errors` для ошибок конкретных полей.
- [x] Зафиксировать назначение основных HTTP-статусов: `400` — некорректный запрос, `401` — нет или неверен токен, `403` — действие запрещено, `404` — ресурс не найден, `409` — конфликт данных, `422` — ошибка валидации.
- [x] Зафиксировать пагинацию для списочных маршрутов через query-параметры `limit` и `offset`. Пример: `GET /api/v1/projects?limit=20&offset=0`.
- [x] Описать ответ списка: объект с `items`, `limit`, `offset` и `total`, чтобы клиент мог построить постраничный интерфейс.

### 4.3. Ресурсы MVP

- [x] Для `auth` и `profile` зафиксировать будущие операции регистрации, входа и работы с текущим пользователем: `POST /auth/register`, `POST /auth/login`, `GET/PATCH /profile`.

### 4.4. Авторизация и доступ

- [x] Зафиксировать публичные операции: регистрация, вход и технический health-check не требуют access token.
- [x] Зафиксировать, что `GET/PATCH /profile`, все операции с проектами, комнатами и покупками, а также представления `overview` и `budget` требуют входа.
- [x] Выбрать JWT access token: после входа API возвращает токен, а клиент отправляет его в заголовке `Authorization: Bearer <access_token>`.
- [x] Указать, что токен не передаётся в URL или теле обычного запроса, а `password_hash` никогда не возвращается клиенту.
- [x] Не добавлять refresh token в MVP. Вернуться к решению при реализации входа, когда будут определены срок жизни сессии и безопасное хранение токенов в клиентах.
- [x] Описать правило владения: пользователь читает и меняет только собственные проекты; комнаты и покупки доступны только через принадлежащий ему проект.
- [x] Указать, что проверку владения выполняет backend в каждом защищённом запросе. Интерфейс клиента не является проверкой безопасности.
- [x] Выбрать поведение для чужих ресурсов: не раскрывать данные и возвращать `404 Not Found`.
- [x] Зафиксировать границу MVP: приглашения, совместный доступ и роли будут добавлены после MVP отдельным изменением контракта и модели прав.

Проверка: прочитать `plan/API.MD` как разработчик клиента. Для каждого ресурса должно быть понятно, какой маршрут вызвать, нужен ли токен, как выглядят дата, деньги, успешный ответ и ошибка. После этого можно отметить пункты раздела как выполненные.

Результат: документ согласован до написания endpoint'ов сценария 1.3.
