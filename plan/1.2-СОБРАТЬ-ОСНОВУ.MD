# 1.2. Собрать основу — подробный план

Этот документ детализирует пункт 1.2 из [основного плана](PLAN.MD). Он рассчитан на обучение: выполняем одну небольшую задачу, проверяем результат и только затем переходим дальше.

## Результат этапа

В репозитории работают API, web-клиент и PostgreSQL. Проект поднимается одной командой Docker Compose, изменения схемы БД проходят через миграции, health-check и тесты выполняются локально и в CI.

## Принципы работы

- Не пишем функциональность проектов и покупок до готовности основы.
- Каждый шаг должен иметь понятный результат и команду проверки.
- Секреты не храним в Git: используем `.env` и `.env.example`.
- Начинаем с минимальной реализации; усложняем, когда появляется практическая потребность.
- Все команды `uv` выполняем из корня репозитория, где находятся `pyproject.toml` и `uv.lock`.

## 3. SQLAlchemy и миграции

В этом разделе появятся три связанных слоя:

```text
модель Account в Python → SQLAlchemy metadata → миграция Alembic → таблица accounts в PostgreSQL
```

SQLAlchemy описывает таблицы классами Python и создаёт подключения к БД. Alembic хранит историю изменений схемы: вместо ручного создания таблиц каждый разработчик применяет одинаковые версии миграций.

### 3.1. Подключение SQLAlchemy

- [x] Создать пакет `backend/app/db` и файл `base.py`.
- [x] В `base.py` создать класс `Base`, наследующийся от `DeclarativeBase`. Все модели будут наследоваться от него.
- [x] Создать модуль подключения, например `backend/app/db/session.py`.
- [x] В нём создать синхронный `Engine` через ленивую функцию `get_engine()`, вызывающую `create_engine(get_settings().database_url)`: URL формируется в `core/config.py`, пароль и хост не дублируются.
- [x] Создать фабрику сессий `get_session()` через `sessionmaker`. Сессия будет единицей работы с БД внутри будущих API-запросов.
- [x] Не создавать соединение при импорте модуля: `create_engine()` только настраивает Engine; настоящее соединение откроется при первом запросе к БД.

На этом этапе используем синхронный SQLAlchemy: у нас драйвер `psycopg`, а первые endpoint'ы пока обычные `def`. Асинхронный вариант намеренно не добавляем, чтобы не смешивать два подхода.

Проверка: маленький временный Python-скрипт или однострочная команда импортирует Engine и выполняет `SELECT 1`. Результат должен быть `1`.

## 4.6. Стиль Python-кода

- [x] Добавить Ruff как dev-зависимость и зафиксировать минимальные правила: ошибки Python, стиль и порядок импортов.
- [x] Настроить Ruff в `pyproject.toml`: Python 3.12+, длина строки 100 символов, исключение сгенерированных миграций Alembic.
- [x] Запустить `uv run ruff check .` и `uv run ruff format --check .`; исправить замечания до успешного завершения обеих команд.
- [x] Добавить Git pre-commit hook через `pre-commit`: перед `git commit` запускать `uv run ruff check .` и `uv run ruff format --check .`. При ошибках hook должен завершаться с ненулевым кодом, показывать замечания Ruff и отменять создание коммита; после исправления повторный `git commit` проходит без ручного запуска линтера.
  - Добавить инструмент в dev-зависимости из корня репозитория: `uv add --dev pre-commit`. Команда изменит `pyproject.toml` и `uv.lock`; оба файла должны попасть в коммит, чтобы у всех использовалась одна версия инструмента.
  - Создать в корне `.pre-commit-config.yaml`. В нём объявить два локальных hook (`repo: local`), потому что Ruff уже установлен через `uv`:

    ```yaml
    repos:
      - repo: local
        hooks:
          - id: ruff-check
            name: Ruff lint
            entry: uv run ruff check .
            language: system
            pass_filenames: false
          - id: ruff-format
            name: Ruff format
            entry: uv run ruff format --check .
            language: system
            pass_filenames: false
    ```

    `language: system` запускает команду в текущем окружении проекта, а не создаёт отдельное виртуальное окружение pre-commit. `pass_filenames: false` важен: команды сами получают корень проекта (`.`), поэтому hook проверяет все файлы по тем же правилам, что и ручной запуск.
  - Установить hook в локальный Git-клон командой `uv run pre-commit install`. Она создаст/обновит `.git/hooks/pre-commit`; этот файл не коммитится, поэтому каждый разработчик после `uv sync` должен один раз выполнить ту же команду.
  - Сразу проверить конфигурацию без создания коммита: `uv run pre-commit run --all-files`. Оба hook должны завершиться со статусом `Passed`.
  - Проверить блокировку: временно внести в Python-файл ошибку Ruff, выполнить `git add <файл>` и `git commit -m "проверка hook"`. Коммит должен быть отменён. Исправить ошибку, добавить файл снова и повторить коммит — теперь он должен пройти. Не создавать намеренно плохой коммит в общей ветке.
  - При обычном `git commit` hook проверяет текущее рабочее дерево. Проверка может занять немного дольше, чем проверка только добавленных файлов, зато поведение совпадает с `uv run ruff check .` и не пропускает ошибку в неиндексированном связанном файле.
  - Если hook сообщает ошибку, сначала выполнить показанную команду Ruff, исправить код либо отформатировать его через `uv run ruff format .`, затем повторить `git add` и `git commit`.
  - Не использовать `git commit --no-verify` в обычной работе: этот флаг намеренно пропускает hook и нужен только для исключительных случаев. Hook является локальной защитой; CI всё равно должен отдельно запускать Ruff, чтобы проверка не обходилась этим флагом.

Шпаргалка по командам и правилам: [Ruff](RUFF.MD).

### 7.3. Разрешить запросы браузера к API

Браузер считает `http://localhost:5173` и `http://localhost:8000` разными origin. Поэтому FastAPI должен явно разрешить frontend для разработки.

CORS (Cross-Origin Resource Sharing) — правило браузера: страница с одного origin не может читать ответ другого origin без явного разрешения сервера.
Origin состоит из схемы, хоста и порта, поэтому `http://localhost:5173` и `http://localhost:8000` различаются только портом, но для браузера это разные источники.

Без CORS `fetch` из Vite-клиента дойдёт до API, но браузер заблокирует доступ React-кода к ответу. Проверки через `curl`, Postman и Swagger UI этой проблемы обычно не показывают: это ограничение именно браузера.

#### 7.3.1. Добавить настройку разрешённых origin

- [x] В `backend/app/core/config.py` добавить отдельную настройку CORS, которая имеет безопасное значение разработки по умолчанию `http://localhost:5173` и не требует переменных `DB_*` при импорте приложения.
Не вызывать существующий `get_settings()` при настройке middleware: он требует параметры БД, а unit-тесты должны уметь импортировать `main.py` без подключения к PostgreSQL.
- [x] Использовать переменную окружения `CORS_ALLOWED_ORIGINS`. Для MVP достаточно строки с origin через запятую, например:

  ```dotenv
  CORS_ALLOWED_ORIGINS=http://localhost:5173
  ```

  Функция настройки должна разбить строку по запятым, удалить пробелы и вернуть список origin. Не добавлять завершающий `/`: `http://localhost:5173/` не совпадает с origin браузера `http://localhost:5173`.
- [x] Добавить `CORS_ALLOWED_ORIGINS=http://localhost:5173` в корневой `.env.example` и задать такое же локальное значение в `.env`.
- [x] Передать переменную в контейнер `api` в `docker-compose.yaml`:

  ```yaml
  environment:
    CORS_ALLOWED_ORIGINS: ${CORS_ALLOWED_ORIGINS}
  ```

  Docker Compose использует `.env` для подстановки значений, но передаёт в контейнер только переменные, перечисленные в `environment` или `env_file`.

Проверка: локальный запуск backend и контейнер `api` получают одинаковый список разрешённых origin.

### 7.7. Подключить готовый web-клиент к Docker Compose

Этот раздел запускает Vite внутри контейнера для локальной разработки. Это не production-сервер: Vite сохраняет hot reload, а исходный код frontend монтируется в контейнер с хоста. Production-раздача собранных файлов через Nginx будет отдельным этапом.

#### 7.7.1. Подготовить Dockerfile frontend

- [x] Создать `frontend/Dockerfile`. Использовать LTS-образ Node.js, например `node:24-alpine`, и рабочую папку `/app`.
- [x] Сначала скопировать только `frontend/package.json` и `frontend/package-lock.json`, затем установить строго зафиксированные зависимости командой `npm ci`. Это позволяет Docker переиспользовать слой зависимостей, если изменился только исходный код.
- [x] После установки зависимостей скопировать исходный код `frontend` в `/app`, открыть порт `5173` и запустить Vite на всех сетевых интерфейсах контейнера:

  ```dockerfile
  FROM node:24-alpine

  WORKDIR /app

  COPY frontend/package.json frontend/package-lock.json ./
  RUN npm ci

  COPY frontend ./

  EXPOSE 5173

  CMD ["npm", "run", "dev", "--", "--host", "0.0.0.0"]
  ```

  Параметр `--host 0.0.0.0` обязателен: без него Vite слушает только loopback внутри контейнера, и опубликованный Docker-порт будет недоступен из браузера на хосте.
- [x] Убедиться, что корневой `.dockerignore` исключает как минимум `frontend/node_modules`, `frontend/dist`, `.env` и `.git`, но не исключает саму папку `frontend`.

Проверка: `docker compose build web` успешно выполняет `npm ci` и не копирует локальный `frontend/node_modules` в образ.

#### 7.7.2. Добавить сервис web в Compose

- [x] В `docker-compose.yaml` добавить сервис `web` со сборкой из корня репозитория и Dockerfile `frontend/Dockerfile`:

  ```yaml
  web:
    build:
      context: .
      dockerfile: frontend/Dockerfile
  ```

- [x] Передать Vite адрес API для браузера и опубликовать порт:

  ```yaml
    environment:
      VITE_API_URL: http://localhost:8000
    ports:
      - "5173:5173"
  ```

  `VITE_API_URL` должен быть именно `http://localhost:8000`, а не `http://api:8000`. Код Vite исполняется в браузере пользователя: для браузера `api` не является именем Docker-сервиса. Имя `api` доступно только другим контейнерам в Compose-сети.
- [x] Добавить зависимость от API и общую сеть:

  ```yaml
    depends_on:
      api:
        condition: service_started
    networks:
      - app-network
  ```

  `service_started` не гарантирует готовность API; это нормально, потому что страница health-check корректно показывает «API недоступен» и умеет повторить проверку.
- [x] Для hot reload добавить development volumes:

  ```yaml
    volumes:
      - ./frontend:/app
      - /app/node_modules
  ```

  Первый volume передаёт изменения исходников из рабочей папки в контейнер. Второй сохраняет Linux-зависимости, установленные внутри контейнера, и не даёт mount с хоста затереть `/app/node_modules`.
> Если на macOS/Windows изменения файлов не подхватываются, добавьте в
> `web.environment` `CHOKIDAR_USEPOLLING=true`, затем перезапустите сервис. Не
> включайте polling без необходимости: он расходует больше ресурсов.

Проверка: `docker compose config` завершается без ошибки и `docker compose config --services` показывает `web`.

## 8. CI

CI (Continuous Integration) повторяет основные локальные проверки на чистом GitHub runner при каждом push и pull request. Это не заменяет локальные pre-commit hook и Docker Compose, а защищает ветку от изменений, которые случайно не проверили на своём компьютере.

На этом этапе workflow состоит из двух независимых jobs:

```text
backend → Ruff + unit-тесты + интеграционные тесты с отдельным PostgreSQL
frontend → npm ci + ESLint + production build
```

Раздельные jobs запускаются параллельно. Ошибка frontend не скрывает ошибку backend и наоборот.

### 8.1. Создать каркас workflow

- [x] Дать workflow понятное имя, например `CI`, и запускать его для `push` и `pull_request`:

  ```yaml

  on:
    push:
    pull_request:
  ```

- [x] Ограничить стандартные разрешения workflow только чтением содержимого репозитория:

  ```yaml
  permissions:
    contents: read
  ```

- [x] Не передавать в CI `.env`, локальные пароли или production secrets. Все значения PostgreSQL в workflow относятся только к одноразовой тестовой БД GitHub runner.

Проверка: файл находится точно по пути `.github/workflows/ci.yml`; GitHub Actions обнаруживает workflow на вкладке **Actions** после первого push.

### 8.3. Job backend: PostgreSQL для интеграционных тестов

- [x] В job `backend` добавить GitHub Actions service container PostgreSQL. Service container — это временный отдельный контейнер с PostgreSQL, который GitHub запускает рядом с job и удаляет после её завершения. Он нужен только для интеграционных тестов: unit-тесты из п. 8.2 по-прежнему могут выполняться без PostgreSQL.

- [x] Job `backend` запускается непосредственно на Linux runner, а не внутри `container:`. Поэтому опубликованный порт сервиса доступен шагам job по адресу `localhost:5432`:

  ```text
  шаг `uv run pytest` на runner
          │
          └── postgresql+psycopg://…@localhost:5432/apartment_test
                                      │
                                      └── service container PostgreSQL
  ```

  Если в будущем job будет выполняться внутри собственного `container:`, адрес изменится на имя сервиса `postgres`; не следует механически переносить в такой job `localhost`.

- [x] Добавить `services` на том же уровне YAML, что и `runs-on` и `steps`. Использовать только одноразовые тестовые значения и имя БД с суффиксом `_test`:

  ```yaml
  jobs:
    backend:
      runs-on: ubuntu-latest
      services:
        postgres:
          image: postgres:18
          env:
            POSTGRES_DB: apartment_test
            POSTGRES_USER: postgres
            POSTGRES_PASSWORD: postgres
          ports:
            - 5432:5432
          options: >-
            --health-cmd "pg_isready -U postgres -d apartment_test"
            --health-interval 5s
            --health-timeout 5s
            --health-retries 10
      steps:
        # …шаги checkout, установки зависимостей и тестов
  ```

  Здесь:

  - `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD` используются образом PostgreSQL только при первоначальном создании временного кластера. Это намеренно простые публичные тестовые значения, а не секреты и не значения из `.env`.
  - `ports: - 5432:5432` публикует порт PostgreSQL из контейнера на runner; левая часть — порт runner, правая — порт контейнера. Поэтому URL тестов содержит `localhost:5432`.
  - `options` задаёт health check. GitHub дождётся успешного `pg_isready`, прежде чем начнёт `steps`; без него тесты иногда стартуют раньше готовности PostgreSQL и падают с ошибкой подключения.
  - Название `apartment_test` обязательно: защита проекта разрешает тестовой команде подключаться лишь к имени БД, оканчивающемуся на `_test`.

- [x] Не задавать `DATABASE_URL`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` или `DB_PASSWORD` для этих команд. Они предназначены для обычной конфигурации приложения и могут случайно направить миграции на не-тестовую БД. В CI передаётся только `TEST_DATABASE_URL`.

- [x] Передать один и тот же URL интеграционному набору и `alembic check` через `env` соответствующего шага. Формат URL важен: `postgresql+psycopg` выбирает используемый в проекте драйвер Psycopg, учётные данные совпадают с `POSTGRES_*`, а последняя часть — имя тестовой БД:

  ```text
  postgresql+psycopg://postgres:postgres@localhost:5432/apartment_test
  │                     │        │        │              │
  │                     │        │        │              └─ тестовая БД
  │                     │        │        └──────────────── порт runner
  │                     │        └───────────────────────── runner
  │                     └────────────────────────────────── пользователь и пароль
  └──────────────────────────────────────────────────────── диалект SQLAlchemy и драйвер
  ```

- [x] Запустить интеграционный набор:

  ```yaml
  - run: uv run pytest -m integration
    env:
      TEST_DATABASE_URL: postgresql+psycopg://postgres:postgres@localhost:5432/apartment_test
  ```

  В тесте вызывается `alembic upgrade head`, поэтому миграции применяются к одноразовой `apartment_test` до проверки таблиц. `get_test_database_url()` сначала проверит, что переменная существует и имя БД оканчивается на `_test`; при ошибке команда завершится до подключения. Не применять миграции к внешней БД.
- [x] После интеграционных тестов проверить, что модель и миграции согласованы:

  ```yaml
  - run: uv run alembic check
    env:
      TEST_DATABASE_URL: postgresql+psycopg://postgres:postgres@localhost:5432/apartment_test
  ```

  `alembic check` не создаёт новую миграцию: он сравнивает SQLAlchemy-модели с состоянием миграций. Шаг выполняется после интеграционных тестов, чтобы схема в `apartment_test` уже была приведена к `head`.

- [x] Итоговая последовательность внутри `backend`: быстрые проверки → service PostgreSQL становится healthy → интеграционные тесты с `TEST_DATABASE_URL` → `alembic check` с тем же URL. Не нужен `docker compose up`, локальный `.env` или Docker volume разработчика: всё окружение создаёт и удаляет GitHub Actions runner.

Проверка: CI запускает интеграционные тесты без skip и не использует локальные Docker volumes разработчика. GitHub Actions поддерживает PostgreSQL service containers на Linux runner; для job, работающего на runner, сервис доступен через `localhost`. [Документация GitHub по PostgreSQL service containers](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers)
